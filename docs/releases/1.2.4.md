## Camera control changes included in this build

- A compact button in the USER screen offers standby while a session is active
  and power-on while inactive. Pause/play and two-camera icons, pastel colors,
  a soft shadow and a short color transition keep the action visible.
- Startup and both operator actions share the same nonblocking, touch-sized
  confirmation component. Not now is the default and Escape action. Repeated
  clicks do not open duplicate dialogs within each prompt path. Operator actions
  reject a confirmation if the session generation has changed. Startup checks
  only that shutdown has not begun and the session is still inactive when
  confirmed; it does not reject an intervening active/inactive session cycle.
- Standby reuses the existing session shutdown path; power-on reuses session
  start, including its existing delayed starting-position moves. This does not
  cut electrical power or change SessionService's camera ordering.
- Standby requested is not confirmation that physical cameras powered down.
  Check both cameras. STOP movement remains a separate action.
- The standalone PTZ panel self-test does not require the main session button.

This version includes other changes already on main since 1.2.3, including
operator Help and preset gesture changes listed in CHANGELOG.md. The list above
is the camera-button scope, not an exhaustive audit of that whole interval.

## Before tagging or installing

1. Review the final exact commit and required CI, including CLI selftest and
   release readiness. Record current candidate evidence without clearing blockers
   by editing statuses. If the gate remains blocked, do not bypass it to publish.
2. Generate and verify the final source/package checksums and SBOM against that
   commit. Do not reuse 1.2.3 tags, release assets or checksums.
3. Confirm the installed ref and launch path. Retain verified installation,
   configuration and data backups off the Pi before updating. For an existing
   product installation with install-state.env, the installer automatically
   creates a local config/data ZIP before GUI shutdown and tree replacement.
   Failure aborts those steps unless --skip-pre-update-backup is explicitly used;
   earlier setup/dependency changes may already have occurred. This guard does
   not apply to first installs, dev mode or an in-place source/install tree. The
   ZIP excludes code and secrets and is not an SD image. It does not replace a
   verified backup off the Pi.
4. With Marco present and outside live use, verify USER power-on and standby for
   both real cameras, cancel/default actions, startup delay, Home/preset behavior,
   touchscreen, disconnect/recovery and existing STOP behavior.
5. Record the target Pi/OS/Python, actual acceptance result and recovery route.
   No stable release without real hall-Pi acceptance. A code rollback alone does
   not undo runtime-data changes; restore only through the verified backup path.

## Scope of supervised target-Pi preparation

A read-only installer preflight from the reviewed full source SHA may collect
Pi/OS/Python/X11/dependency evidence without replacing the working installation.
The wrapper's `--guide` and `--check` paths do not run doctor or camera probes.
Installer preflight PASS is not release-readiness PASS or camera acceptance.

A supervised local installation rehearsal is distinct from publication or
customer handover. It must retain the working build, configuration, runtime data
and protected credentials off the Pi, verify the actual launch path, have a
supported recovery route, pass installer preflight and have Marco present with
physical STOP available. Do not run another controller beside the working GUI.
An unresolved backup, source identity or target prerequisite stops the update.
Do not use `--allow-dirty` or `--skip-pre-update-backup` to make it proceed.

The release-readiness gate remains unchanged and failing until real target
results support its rows. No publication, stable claim, target doctor PASS,
network PASS or hardware acceptance is granted by this preparation.
