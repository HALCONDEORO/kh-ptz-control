# Branch Protection Policy

This policy defines the intended GitHub protection rules for `main`.

Actual GitHub repository settings may need to be applied manually by a maintainer with repository administration permissions.

## Scope

Protect:

```text
main
```

Use feature branches for normal work. Do not commit directly to `main`.

## Required Rules

Recommended `main` branch rules:

```text
[ ] require a pull request before merge
[ ] require status checks to pass before merge
[ ] require conversation resolution before merge
[ ] block force pushes
[ ] block branch deletion
[ ] dismiss stale approvals when the PR changes where practical
[ ] require CODEOWNERS review for security, deployment, installer and runtime data paths where practical
[ ] include administrators if the workflow can tolerate it
```

## Required Checks

Required checks should start conservative and expand as the workflows stabilize.

Immediate required checks:

```text
pytest
ruff
markdown links
startup smoke
tests-and-critical-lint
```

Add these as required when they are stable and not noisy:

```text
repo hygiene / secret scan
dependency audit
bandit
pip-audit
release gate
```

Do not make a check required until it is reliable enough that maintainers can distinguish real failures from infrastructure noise.

## Review Policy

Minimum review policy:

```text
[ ] one approving review before merge
[ ] no self-approval as the only approval for customer-facing changes
[ ] CODEOWNERS review requested for high-risk paths
[ ] security/deployment-sensitive changes get human review even when generated by automation
```

High-risk paths include:

```text
runtime/installer/
runtime/systemd/
runtime/cli.py
backup / restore code
config loader and migration code
licensing code
VISCA / camera control code
customer runtime data paths
GitHub workflow and release automation
```

## Dependabot And Automation

Dependabot PRs must use the same review and CI path as human PRs.

Policy:

```text
[ ] no automatic merge at first
[ ] no bypass of required checks
[ ] review major version updates manually
[ ] treat security updates as urgent but still reviewable
```

## Emergency Hotfixes

Emergency hotfixes are allowed only when delaying the fix is riskier than the abbreviated process.

Hotfix requirements:

```text
[ ] create a focused hotfix branch
[ ] explain customer impact
[ ] run the smallest safe affected-area checks
[ ] record skipped checks and why
[ ] merge through PR unless GitHub is unavailable
[ ] tag the validated hotfix commit if it is deployed
[ ] document rollback
```

If branch protection must be bypassed, record who approved it, why it was necessary and which follow-up validation is required.

## Draft PRs

Draft PRs are allowed for work in progress, but they must not be merged until:

```text
[ ] converted to ready for review
[ ] checks are green or exceptions are documented
[ ] review policy is satisfied
```

## Manual Application Checklist

Use this checklist when applying GitHub settings:

```text
[ ] main branch rule created
[ ] PR before merge enabled
[ ] required status checks selected
[ ] force pushes blocked
[ ] deletion blocked
[ ] review requirement enabled
[ ] CODEOWNERS review enabled where practical
[ ] administrators included or exception documented
[ ] hotfix bypass process documented
```

## Follow-Up

When new security, dependency or release workflows become stable, update this policy and branch protection settings in the same release-readiness pass.
